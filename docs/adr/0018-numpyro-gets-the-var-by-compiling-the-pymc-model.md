# NumPyro gets the VAR by compiling its PyMC model to JAX, one way

A NumPyro user wants an Impulso VAR as one part of a larger NumPyro model (#404), as a PyMC user gets one through `VAR.build_in_model` ([ADR-0016](0016-embeddable-var-path.md)). The VAR stays defined once, in PyMC, by `build_in_model`. `VAR.compile_for_numpyro` takes `build_in_model`'s arguments except `endog`, opens a fresh `pm.Model`, calls `build_in_model` with a symbolic placeholder for `endog`, and compiles two JAX functions from that model with `pymc.sampling.jax.get_jaxified_graph`, the conversion `pm.sample(nuts_sampler="numpyro")` uses. The first is the joint log-density: priors, Potentials, likelihood and PyMC's transform corrections. The second maps the same inputs to the quantities the block records: `B`, `intercept`, `B_exog`, `L`, `nu` and `latent`. It returns both as a `CompiledNumPyroBlock`. The route runs one way, from PyMC to NumPyro. No NumPyro code is written for any VAR variant, so a change to a prior, a volatility process or an observation error distribution reaches NumPyro users with no NumPyro-specific code.

**A call.** The caller calls the block inside a NumPyro model function and passes `endog`: observed data or an array the NumPyro model computed. The block declares one NumPyro sample site per PyMC value variable, adds the compiled log-density with `numpyro.factor`, records the quantities with `numpyro.deterministic` under their unprefixed posterior-schema names, and returns them as a `VARModelValues`. The PyMC model is built and compiled once, in the compile step, never inside the NumPyro model function, however often NumPyro traces it.

**NumPyro parameters are declared on PyMC's unconstrained scale.** Each site holds a PyMC value variable, the free variable after PyMC's transform (`sigma_sd_log__`, for example, is the log of the innovation standard deviations), with NumPyro's `ImproperUniform` on the real line as its distribution. The compiled log-density keeps PyMC's transform corrections, so NumPyro's log-density of the model equals PyMC's at the same parameter values. The parity tests check that for every embedded-path variant. No table maps PyMC supports to NumPyro constraints, and PyMC's own NumPyro sampler handles transforms the same way. Constrained values reach the trace through the recorded quantities. The sites are named `unconstrained/<value-variable name>`, because the untransformed value variables `B`, `intercept` and `B_exog` carry the posterior-schema names, and NumPyro refuses two sites with one name.

**`endog` arrives at call time, so the embedded-path rules apply.** `build_in_model` always takes its symbolic-`endog` path here: `endog_scales` is required, `lags` must be an integer, the volatility process must be `Constant`, latent series require Gaussian errors, and the likelihood is the Potential `obs`. The compile step raises these refusals, with `build_in_model`'s messages, by calling `build_in_model` before it compiles anything. `exog` is fixed at compile time, because the exogenous prior scales with each regressor's sample standard deviation ([ADR-0012](0012-exog-prior-scales-with-data.md)), so a call takes only `endog`.

**With latent series the compile step takes the row count of `endog`.** Without latent series the placeholder's row count is unknown, and one block accepts an `endog` of any length. With latent series the length of the latent path's `scan` is then unknown too, and `jax.jit`, which NumPyro applies to every model, cannot compile it. Of the three latent cases checked (one latent series with one lag, one with two lags, two with two lags), PyMC 6.2 raises `TypeError: Shapes must be 1D sequences of concrete values` in all three, and PyMC 5.28 raises that error or `IndexError: Slice entries must be static integers` in two. The compile step therefore takes `n_endog_rows`, the number of rows of the `endog` each call receives, and is still the one place where the model is built and compiled. A call whose `endog` has another number of rows raises `ValueError`.

**Terms with a zero-gradient override are added through `jax.lax.stop_gradient`.** ADR-0016 gives the `latent_stationarity` Potential a zero gradient by overriding the gradient of an `OpFromGraph`, because PyTensor cannot differentiate the non-symmetric `eig` inside it. PyTensor's JAX conversion inlines the `OpFromGraph` and drops the override, so `jax.grad` of a single JAX function for the whole log-density raises `NotImplementedError: Derivatives of non-symmetric eigenvectors are only valid under assumptions on the input that JAX cannot check`. #404 expected JAX to need no override; it does. The code that builds a term with a zero-gradient override also declares it, with `impulso._zero_gradient.declare_zero_gradient`, a flag on the term's PyTensor variable. The compile step compiles every declared term as one JAX function of its own and adds it to the rest of the log-density on `jax.lax.stop_gradient` copies of the inputs (`numpyro_block.add_with_zero_gradient`). The values of those terms count, their gradient is zero, and the block's gradient equals PyMC's `compile_dlogp`, which applies the override. The compile step names no term, so a future term with a zero-gradient override needs only the declaration. Detecting the override from the graph instead was rejected: a term that contains an overridden `OpFromGraph` can still depend on the parameters through other operations, so finding the `OpFromGraph` does not show that the whole term's gradient is zero. With this split NumPyro's NUTS samples the latent cases that carry the Potential, which `pm.sample(nuts_sampler="numpyro")` cannot (#378).

**Initial values come from PyMC.** NumPyro sets initial values on the sampler, not in the model. `CompiledNumPyroBlock.initial_point` holds PyMC's initial point keyed by site name, on the unconstrained scale, for NumPyro's `init_to_value`. It includes the stationary start for `B` that ADR-0016 sets when a latent own-lag prior mean lies outside the stationary region; NumPyro's default random start can fall outside the region and has to retry.

**The handoff is `FittedVAR.from_posterior`, unchanged.** NumPyro samples carry no dimension names, and the posterior schema checks `B`, `intercept` and `B_exog` by dimension name. `CompiledNumPyroBlock.posterior_from_samples` names the sample axes `chain` and `draw`, gives each recorded quantity the dimension names and coordinate labels of the PyMC model, and writes the intercept on `var` with zeros for the equations `intercept_equations` excludes, as the PyMC model's mean has them. It drops the block's `unconstrained/` sites, whose `/` ArviZ 1 refuses in a variable name, and the log-density site. The caller obligations ADR-0016 sets for embedding callers apply as written: supply a `VARData`, with a plug-in column for each latent series, and pass `error_dist=spec.resolved_error_dist`, without which `FittedVAR.from_posterior` accepts a Student-t posterior as Gaussian.

## Considered options

- **Native NumPyro models** — rejected. A NumPyro implementation of every VAR variant next to the PyMC one means every prior, volatility process, observation error distribution and latent-series feature is written and tested twice, and the two implementations can drift apart.
- **A model-building layer with one implementation per library** — rejected. Model code written against an abstraction still needs each primitive implemented once per library, and the abstraction must cover what PyMC and NumPyro do differently: transforms, Potentials, `scan` and initial values. It costs what native NumPyro models cost, plus the layer.
- **Converting NumPyro models to PyMC** — rejected. The VAR is written in PyMC, and the need is to use it in NumPyro; the conversion runs the other way.
- **Declaring parameters as NumPyro improper uniforms on their supports** — rejected. Removing PyMC's transforms and declaring each variable as NumPyro's `ImproperUniform` on the matching support keeps constrained values as the sampled variables. It needs a table from PyMC supports to NumPyro constraints, which every new prior or volatility process would have to extend.
- **Re-specialising the compiled functions to each call's row count** (latent series) — rejected. Cloning the graphs at call time with `endog` and the value variables at static shapes, converting them to JAX and caching them by shape works under `jax.jit` and needs no `n_endog_rows`. It converts the model inside the NumPyro model function, on the first call for each row count, where the compile step exists to build and compile it once, outside.

## Consequences

- **No prior predictive sampling of the VAR inside NumPyro.** The VAR's sites have no NumPyro distribution to draw from, so `numpyro.infer.Predictive` without posterior samples cannot draw the VAR's parameters. Compiling PyMC's prior sampling to JAX as well could add it without code per model.
- **No `numpyro.handlers.do` on the VAR's parameters.** `do` ignores deterministic sites such as `B`, `intercept` and `L`. On an unconstrained site it cannot remove the parameter's prior, which is part of the compiled log-density.
- **The embedded-path refusals apply**: a string `lags`, a volatility process other than `Constant`, and Student-t errors with latent series.
- **`exog` is fixed at compile time.** A block serves one set of exogenous regressors.
- **With latent series a block serves one row count of `endog`.**
- **The latent-block stationarity constraint needs JAX's non-symmetric eigendecomposition.** JAX computes it on CPU and GPU (on a GPU it calls LAPACK on the host CPU by default) and does not support it on TPU. No GPU run has been tested. One latent series with `n_lags = 1` has no eigendecomposition ([ADR-0017](0017-truncated-own-lag-for-one-latent-ar1.md)).
- **Every chain starts at the same point** when the caller uses `init_to_value(values=block.initial_point)`, because `init_to_value` does not jitter.
- **Importing PyTensor's JAX backend switches JAX to 64-bit floats** (`jax_enable_x64`) when PyTensor's `floatX` is `float64`, its default. The switch is global, so it reaches the rest of the caller's JAX code.
- **Site names are not prefixed.** Two VARs in one NumPyro model need a `numpyro.handlers.scope(prefix=...)` each. The recorded names then carry the prefix, and `posterior_from_samples` refuses samples without the unprefixed names.
- **JAX and NumPyro stay optional.** They are the `numpyro` extra. The compile step imports them lazily and raises an `ImportError` naming the missing packages. The dev dependency group holds both, so the tests of the compiled NumPyro block run in the `tests-and-type-check` CI job, and the docs dependency group holds both for the tutorial.
- `VAR.fit` does not sample with NumPyro; `NUTSSampler` offers no NumPyro backend. That is a separate change.
